Strong Capability ownership

Give the tool capability registry one owner

The tool contract, availability, executor map, provider definitions, and OpenResponses projection are spread across several modules. A capability change can cross multiple seams before it reaches a model or an approval action.

Deepening opportunity: concentrate capability resolution, dispatch, and model projections behind one deep module. Keep protocol loops focused on their transport behavior.

Why it matters

  • Locality: one capability change has one primary home.
  • Leverage: both protocol loops consume the same resolved result.
  • Consistency: availability context such as developerMode is supplied once.
  • Tests: dispatch and policy get one stable seam.

Evidence to preserve in an ADR

toolRegistry.ts:331-430 already contains transitional construction and resolution helpers. ToolExecutor.ts:43-217 still builds a large executor map, while ProviderRegistry.ts:163-192 resolves provider definitions separately. useMessageActions.ts:614-640 resolves the model-facing set, then creates separate executors at lines 739, 878, and 1496.

Expected wins

  • Locality: one turn lifecycle is readable in one place.
  • Leverage: callback and persistence policy is shared by both protocols.
  • Tests: request assembly and approval flows can run without React.
  • Less duplication: executor lifecycle and continuation decisions stop being wired repeatedly.

Deletion test

Deleting the hook’s orchestration responsibilities would remove a real concentration of policy. Deleting only a helper and moving its statements elsewhere would not improve depth; the candidate is worthwhile only if the new module owns the complete turn lifecycle.

Observed pressure

historyBuilder.ts:21-179 maintains two serialization paths. The default toolHistoryMode is elide, and the same request can then be budgeted again at useMessageActions.ts:614-663 and AgentLoop.ts:235. This is a real seam for information loss, not just a style concern.
