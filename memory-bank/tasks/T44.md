## Description

Create a browser-based development surface for the React chat UI so components
and important states can be built and viewed without opening the full Obsidian
application. Keep Obsidian-specific APIs behind a small host boundary so the
standalone surface does not become a second production runtime.

The first preview target is the extracted layout and presentational components,
not the current `ChatApp` controller with a fake implementation of every
Obsidian service.

## Subtasks

### T44.1: Define the host boundary
- Move `ChatPluginLike` out of `ObsidianAIChatView.ts` into a neutral host/types
  module.
- Define the smallest interfaces needed by presentational components:
  markdown rendering, notices, icons, vault reads, and workspace actions.
- Keep the production adapter backed by Obsidian APIs.

### T44.2: Complete the T22 layout extraction prerequisite
- Coordinate with T22 Phase 5 to extract `ChatLayout`, `ChatToolbar`,
  `ChatMainArea`, and `ChatOverlays`.
- Keep `ChatApp` as the controller/composition layer.
- Do not duplicate relay, session, or streaming state in preview components.

### T44.3: Add standalone fixtures
- Add deterministic fixture data for empty, normal, streaming, tool approval,
  error, multi-agent, relay-only, and mobile-sized states.
- Ensure fixtures contain no API keys, vault contents, or live relay state.

### T44.4: Add the browser preview workflow
- Use Storybook as the persistent component workshop.
- Continue using Vitest/jsdom for fast behavior tests.
- Add Vitest Browser Mode or Playwright only where real-browser behavior is
  needed, especially scrolling and mobile viewport checks.

### T44.5: Verify the boundary
- Verify preview rendering and interaction without importing the real Obsidian
  runtime into the standalone entry point.
- Keep full Obsidian verification as a separate host-integration gate.

## Implementation Details

### Tool boundary

Storybook is the primary persistent preview tool. Existing Vitest and React
Testing Library tests remain the fast behavior layer. Vitest Browser Mode or
Playwright is a secondary real-browser layer, not a replacement for the
existing unit tests.

### Dependency direction

```text
ObsidianAIChatView
  -> production ChatHost adapter
  -> ChatApp/controller
  -> ChatLayout and presentational components

Storybook fixture host
  -> fixture ChatHost adapter
  -> ChatLayout and presentational components
```

The standalone path must not import `obsidian`, `MarkdownRenderer`, or the
production `ItemView` boundary just to render presentational states.

### Scope boundary

This task does not recreate the complete Obsidian workspace, vault, editor,
relay server, or provider API in a browser preview. Those remain integration
concerns and should be tested with focused mocks or in Obsidian itself.

## Issues and Blockers

- `ChatApp.tsx` and several child components still combine controller logic or
  direct Obsidian APIs with presentation. T22 Phase 5 must reduce that coupling.
- Obsidian's Markdown renderer and DOM helpers require an adapter or a preview
  renderer substitute; the production renderer must not be silently replaced
  in the Obsidian path.
