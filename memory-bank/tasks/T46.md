# T46 — Core Orchestration Decomposition
*Created: 2026-08-17 06:07 IST*
*Last Updated: 2026-08-27 13:21 IST*

**Status**: 🔄 **ACTIVE — plan refreshed after architecture review**
**Priority**: MEDIUM
**Dependencies**: T22 (complete), T23 (complete), T60a, T48b, T48c

## Problem Statement

The core orchestration layer of obsidian-ai has grown into several dense
modules during agentic tool calling and surface work (T43/T44). The current
size scan and architecture review identify these primary candidates:

| File | Lines | Problem |
|------|-------|---------|
| `src/agent/ToolExecutor.ts` | **2,159** | Mixes capability construction, dispatch, validation, and many unrelated tool domains |
| `src/hooks/useMessageActions.ts` | **1,533** | Mixes UI state with request assembly, context policy, protocol loops, persistence, and approval |
| `src/main.ts` | **1,785** | Plugin lifecycle, registration, storage, event wiring, and integration setup remain concentrated |
| `src/api.ts` | **765** | Provider, history, streaming, and editor integration responsibilities remain together |

These files are outside the completed T22 UI decomposition and T23 settings
decomposition. They need a responsibility-led decomposition pass, with T60a
owning capability semantics and T46 owning the physical module arrangement.

## Guiding Principles

1. **Orchestration vs Implementation**: The orchestrator decides *when* to do
   something; the handler decides *how*. Never mix the two.
2. **Category-based grouping**: Tools group by domain (note content, discovery,
   vault management, bulk operations), not by when they were added.
3. **Factory over switch**: Provider creation is a factory pattern, not a
   series of `if/else` blocks.
4. **Lifecycle over logic**: `main.ts` should coordinate lifecycle events, not
   contain business logic.

## Phase 1: Capability Registry and ToolExecutor Decomposition

### Goal
Reduce `ToolExecutor.ts` from 2,159 lines to a thin compatibility facade
without preserving its
current metadata duplication. T60a defines the canonical registry and T60c
defines the validated execution pipeline; this task owns their physical module
decomposition.

### Extract
- `src/agent/tools/handlers/note-handlers.ts` — read, edit, append, create, patch, edit_section
- `src/agent/tools/handlers/discovery-handlers.ts` — search_notes, list_notes, get_note_metadata, count_notes
- `src/agent/tools/handlers/vault-handlers.ts` — create_folder, move_note, delete_note, list_folders
- `src/agent/tools/handlers/bulk-handlers.ts` — create_notes
- `src/agent/tools/handlers/session-handlers.ts` — search_past_sessions
- `src/agent/tools/ToolResolver.ts` — `resolveNote()` and path utilities (extracted from ToolExecutor)
- `src/agent/tools/registry.ts` — canonical capability descriptors and availability
- `src/agent/tools/pipeline.ts` — validate/authorize/preflight/execute state machine
- `src/agent/tools/serializers.ts` — AI SDK and OpenResponses projections
- `src/agent/tools/formatters.ts` — model and UI result formatting

### Remaining in ToolExecutor.ts
- Thin compatibility facade delegating to the T60 registry/pipeline
- Construction of execution context from Obsidian services

## Phase 2: api.ts Decomposition

### Goal
Reduce `api.ts` from 765 lines to ~300 lines after the higher-priority
capability, history, and turn-lifecycle work.

### Extract
- `src/api/providers.ts` — `createLanguageModel()` + all provider factories
  (openai, ollama, gemini, azure, custom, openrouter, kimi)
- `src/api/history.ts` — `MessageQueue` class + management
- `src/api/streaming.ts` — `streamChatWithTools()` and stream event translation

### Remaining in api.ts
- `ChatAPIManager` class as orchestrator only
- Profile validation
- Connection testing
- Editor integration (or move to a bridge module)

## Phase 3: main.ts Decomposition

### Goal
Reduce `main.ts` from 1,785 lines to a lifecycle coordinator of roughly
300–400 lines.

### Extract
- `src/ui/registration.ts` — Leaf/view registration (`registerView`, `addCommand`)
- `src/ui/events.ts` — Event handlers (`onLayoutReady`, workspace change, file open)
- `src/lifecycle/storage.ts` — Storage initialization (`createStorage`, migration)

### Remaining in main.ts
- `ObsidianAIPlugin` class as lifecycle coordinator
- `onload()` — delegates to registration, storage, event modules
- `onunload()` — cleanup

## Audit Update — 2026-08-25

Handler extraction alone is insufficient. Prompt descriptions, schemas,
dispatch, previews, formatting, risk, and availability must converge on the
canonical registry so this task does not split one god class while retaining
several independent sources of truth.

## Architecture Review Update — 2026-08-27

The recommended implementation order is:

1. Complete the remaining T60a registry ownership and projection work.
2. Physically decompose `ToolExecutor.ts` around the T60 registry and pipeline.
3. Consolidate model-history policy through T48b/T48c/T62a and the T64b
   retention evidence.
4. Execute T46a to move request assembly and turn lifecycle out of
   `useMessageActions.ts`.
5. Reassess `api.ts` and `main.ts` as separate later phases.

Do not split by arbitrary function groups. Each extracted module must own a
complete concept and leave the original file as a thin composition layer.
