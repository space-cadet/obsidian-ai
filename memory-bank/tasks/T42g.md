# T42g: Sync Visibility & Observability

## Goal

Make sync fully legible to the user: live transfer progress (bytes + derived rates), per-file activity, structured errors, conflict/overwrite detail, and browsable history — across **all** trigger paths (sidebar panel, auto-sync-on-save, settings Sync Now, command palette, startup init).

Directed by Deepak 2026-09-19 (blocking v1.6.0): "when it runs it doesn't show the user any information. What is being downloaded, uploaded, overwritten. Transfer rates, stats, logs. Nothing."

## Relationships

- Parent **T42** (Remote Chat Storage & Sync). Siblings T42a–d (index, atomic writes, concurrency, server signature).
- **T58d** (Unified Sync Progress/Dry-Run/Rebuild UX) built the per-operation row progress (pending→active→done/skipped/error, shimmer, sticky 100% bar) — T42g builds observability on top of that foundation, not in place of it.
- Distinct from **T42e** (dry-run mode) and **T42f** (⛔ superseded standalone sidebar, replaced by T58).
- Reference implementation: `code/obsidian-syncit` (space-cadet), observability UI shipped 2026-09-01 (`156a125`).

## Background — audit findings (2026-09-19)

What exists: `triggerSync` (src/lifecycle/sync.ts) is fully instrumented — per-session logs with titles, `SyncProgressSnapshot` (counts + elapsedMs), `SyncLogger` (local file + remote append), final summary toast. `ChatSyncPanel` (v2) is the only live UI.

Gaps:

1. **Every non-panel path is toast-only.** Auto-sync after save (debounced 3s — the most common path), settings Sync Now (`remoteStorageSettings.ts:377`), command palette (`registration.ts:149`) call `triggerSync()` with no callbacks. No running indication; final 6s toast only.
2. **Auto-sync failures are silent** — swallowed to the file logger (`scheduleAutoSync` catch in `persistence.ts`). User never sees a failure.
3. **No bytes, no rates.** `SyncProgressSnapshot` tracks counts only. Byte/rate data does not exist in the data model.
4. **Overwrites are opaque.** Conflicts counted (⚡n) but no per-conflict resolution detail (which side won, what was overwritten).
5. **No in-app log viewer.** `SyncLogger` history is written to files; nothing in-app reads it back.
6. **Startup init is silent** — ~4.1s WebDAV init (T24 notes) blocks startup with zero feedback.
7. **`SyncProgressModal` is dead code** — `useModal: true` never passed by any caller. Wire it or delete it.

## Reference patterns from obsidian-syncit

Port patterns, not verbatim code:

- **Byte accounting**: `SyncPlan.uploadSize/downloadSize` (planned, from `FileEntity.size`), `SyncResult.uploadedBytes/downloadedBytes` (actual). Rates derived = bytes ÷ elapsed.
- **Structured failures**: `SyncOperationFailure{operation: upload|download|conflict|local-delete|remote-delete, path, phase: transfer|delete, message, details}` — persisted, drives an errors surface.
- **Reconciliation model**: `ReconciliationItem` + `ReconciliationReason` (no-baseline-local-only/remote-only/conflict, possible-remote/local-deletion) + `ReconciliationDecision` (use-local/use-remote/keep-both/skip). Answers "what's being overwritten."
- **SyncLogger**: leveled + categorized, async queued flush, rotation by max age (days) AND max size (MB), backup in plugin dir, tested. obsidian-ai's logger has no rotation.
- **Five-surface sidebar blueprint**: sync (controls) / activity (recent ops) / errors (failures) / reconciliation (decisions) / progress (bar + meta).

Constraint in both codebases: no streaming Content-Length hooks in either WebDAV adapter → "live KB/s mid-transfer" is NOT free; totals + derived rate are the honest v1. Real-time throughput needs new adapter work (defer unless Deepak insists).

## Scope

- **P1** — Status-bar sync indicator (Obsidian `addStatusBarItem`): idle / syncing ↑n ↓n / error / last-sync; fed at engine level so it covers every trigger path; click → panel.
- **P1** — Failure surfacing: auto-sync errors visible (status-bar error state + click-to-retry), not file-log whispers.
- **P2** — Byte counters: adapter + snapshot += uploadedBytes/downloadedBytes (+ planned sizes); totals + derived rate in panel.
- **P2** — Conflict detail: resolution + explicit "overwritten" marking per conflict; post-run conflicts section.
- **P2** — Sync log viewer: in-app view of SyncLogger history (last N sessions, filter by direction/status).
- **P3** — Startup "Sync: connecting…" status during engine init.
- **Cleanup** — wire or delete orphaned `SyncProgressModal`.
