## Description

Define and implement a versioned Integration Provider API through which normal
Obsidian plugins can contribute narrowly scoped domain tools to Obsidian AI.
The provider owns domain execution, configuration, credentials, and manual UI;
Obsidian AI owns model-facing schemas, user approval, execution policy, result
rendering, and privacy-aware operation logging. Obsidian Git is the first
provider candidate, not a reason to expose arbitrary shell commands.

## Acceptance Criteria

- [ ] A versioned provider contract supports capability discovery, registration,
  compatibility reporting, and cleanup when a provider is unavailable.
- [ ] Provider tools are namespaced, have structured schemas and declared risk
  classes, and cannot register an arbitrary command-execution escape hatch.
- [ ] Obsidian AI applies its own approval policy and audit logging to every
  provider operation; a provider cannot self-authorize a remote write.
- [ ] Providers retain credentials and raw domain data; prompts and default
  audit records omit credentials, note contents, and raw diffs.
- [ ] The normal non-AI UI and the AI tool path share the same provider-domain
  implementation rather than duplicating Git or vault behavior.
- [ ] A compatible Obsidian Git provider supplies bounded status, history,
  changed-file, explicit-stage, commit, pull, and push capabilities.
- [ ] Disabled, absent, or incompatible providers do not break chat and give a
  clear, actionable availability result when invoked.

## Implementation Details

- T39a defines the host registry, provider descriptor, lifecycle, schema/risk
  validation, availability state, settings controls, and host-side tests.
- T39b adapts the existing `obsidian-git` GitManager as the first provider. It
  exposes narrow public operations and typed progress events; it does not pass
  its private classes or credentials through the AI boundary.
- Initial risk policy: status/history/changed-files are read-only; stage and
  commit require a previewed plan; pull and push require prominent explicit
  approval; force-push, arbitrary remote changes, credential changes, and
  repository initialization are out of scope.
- The host must negotiate an `apiVersion`, namespace tool IDs such as
  `git.status`, and refresh discovery safely across plugin load/unload order.
- The provider-facing UI is a generic Integrations settings section plus
  descriptor-driven pending-operation and inline result cards. It does not add
  a second Git sidebar to Obsidian AI; Git configuration stays with the Git
  provider.
