The persisted transcript remains untouched; only the model-facing history is
selected against the request budget. The newest messages are retained first,
with a configurable response reserve and tool/schema overhead estimate. Full
provider-window discovery and attachment-aware accounting remain open.

## 500k-token incident — 2026-08-25

A real-world conversation with 17 sequential `search_notes` calls consumed
~500k tokens. Root cause analysis (`T60b`) revealed that the OpenResponses
loop resubmits the full original input on every tool round — a protocol bug
unrelated to budget sizing. Token-budgeted context building remains necessary,
but it cannot compensate for duplicate input resubmission. The true fix is in
`T60b` (stateful continuations via `previous_response_id`).

## Architecture Review Update — 2026-08-29

The fresh review keeps request budgeting under this task but identifies a
shared model-history boundary as the next design step. Budgeting must be
applied once as part of the model-ready projection, alongside T48b replay and
T48c compaction, rather than independently in each protocol loop.

The first implementation now routes the main request and agent continuations
through shared model-history budget helpers. Provider-window discovery and
attachment-aware accounting remain open.

## Fidelity Horizon Analysis — 2026-09-09

The attached conversation audit confirms that request budgeting must run once
on the fully serialized model-ready request before every provider call,
including hidden tool-loop iterations and continuation calls. Large attached
notes and tool results need limits before serialization; after a tool turn,
the full result should leave active replay context while remaining available by
reference for exact retrieval.

Add acceptance coverage for per-iteration request budgets, attachment/result
eviction, and stable retrieval references. This complements T48b's canonical
serializer and T48c's compaction policy rather than adding another budget rule.

## Controlled production telemetry — 2026-09-09

The same-model `gpt-oss-120b` baseline reported 7,272 provider input tokens
with no tool call. A small `read_note` result kept the next request at 7,272
input tokens, while a result capped at 2,000 local tokens raised the next
request to 9,402. These runs had `historyTokens: 0`, so they validate tool-loop
request composition but not non-zero `maxRequestTokens` history trimming.

The long-context comparison with `maxRequestTokens: 0` and a non-zero budget
remains an open acceptance test.

## Implementation and Diagnostic Update — 2026-09-10

- Semantic-compaction input now uses the shared bounded tool-result projection,
  with an 8,000-token ceiling and a 1,200-token per-result allowance.
- The diagnostic confirmed that cumulative provider usage does not trigger
  compaction: the largest recorded `historyTokens` value was about 8,861,
  despite 239,998 cumulative provider tokens.
- A separate oversized-context defect remains: context resolution reads and
  expands a large note before the turn abort controller exists. Add preflight
  cancellation, attachment/context limits before serialization, and fail-fast
  request-budget checks before claiming this acceptance complete.
