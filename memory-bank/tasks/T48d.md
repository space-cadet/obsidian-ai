# Task: T48d — Context-Aware Usage Display and Provider Reconciliation
*Created: 2026-08-23 02:02:32 IST*
*Last Updated: 2026-09-10 03:25:00 IST*
*Status: 🔄 ACTIVE*

## Objective
Make the UI distinguish current-request estimates, cumulative provider usage,
and saved-message estimates.

## Acceptance Criteria
- [ ] Provider prompt/completion/total usage is displayed when available
- [ ] Fallback estimates are explicitly labeled as estimates
- [ ] Tool-loop and compaction requests are accounted for where available
- [ ] Session totals do not double-count user or full-request estimates
- [ ] Diagnostics explain why provider totals can exceed visible message totals

## Dependencies
- Depends on: T6a, T48a
- Parent: T48

## Harness integration — 2026-08-26

T64: Context Optimization Benchmark Harness will provide ground-truth token
measurements to reconcile display estimates with provider-reported usage.
The harness's Level 2 (live API) mode captures actual provider usage numbers
for direct comparison against the plugin's fallback estimates.

## Live validation evidence — 2026-08-29

The expanded OpenRouter run showed that local estimates can be much higher than
the provider-reported prompt count. Across 20 requests, the average difference
was -54.7%, with results ranging from -98.88% to +18.54%. The run included the
deterministic compaction projection and recorded `$0.00628440` in provider
reported benchmark cost.

This supports the following display rule:

- Use provider-reported usage when it is available.
- Label local counts as estimates when provider usage is missing.
- Do not silently apply one correction factor to every request.
- Keep diagnostics able to explain why the provider count and visible message
  count can differ.

The compaction result validates the projected request payload only; it does not
include the separate production summary-generation request. The full result
table is recorded in `tasks/T64d.md`.

## Fidelity Horizon Analysis — 2026-09-09

The attached conversation data reports 486,550 provider tokens and 132,492
saved-message estimates. These are different accounting categories; adding
them produces about 619k and can explain the reported ~600k without implying
that the provider received both values. Display and session totals must use
provider-reported per-request usage as the source of truth, with estimates as a
clearly labelled fallback.

Tool-loop iterations and compaction calls should be visible as separate
requests, then rolled into a cumulative total exactly once. Diagnostics should
explain why visible transcript size, request estimates, and provider totals
differ.

## Per-step Debug Telemetry — 2026-09-09

Implemented bounded per-step diagnostics for the native tool-enabled agent
loop. When Debug Mode and `debugTelemetry.includeRequestBreakdown` are enabled,
each assistant message can retain an `agentSteps` export record containing the
step number, local request estimate, tool-schema/history/continuation/tool
result estimates, and per-step provider usage including cached input when
reported. The existing provider-usage and request-estimate export flags still
filter their respective nested fields.

The request estimate is intentionally approximate: provider-reported usage is
the authoritative value. OpenResponses per-step parity remains open because
that loop still needs to expose its usage events as structured step results.

## Controlled production evidence — 2026-09-09

The Debug Mode export contained a valid same-model baseline and matched
small-result/large-result runs. The baseline reported 7,272 provider input
tokens with no tool call. The small-result run reported 7,275 and 7,272 across
its two steps; the large-result run reported 7,285 and 9,402. Per-step provider
usage reconciled exactly with the assistant-message aggregate in the separate
three-step run: 32,279 input, 486 output, and 32,765 total tokens.

The exports also show cached input in some steps, but do not identify which
request component was cached. Local estimates remain approximate and must not
be added to provider totals. Long-history and non-zero request-budget behavior
remain unvalidated.
