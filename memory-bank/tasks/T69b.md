## Description

Evaluate and plan support for connecting Obsidian AI to Claude Code or its
supported local/service interfaces. The task must establish which account,
subscription, API-key, CLI, OAuth, or local-process paths are officially
supported before choosing an adapter architecture.

## Acceptance Criteria

- [ ] Verify the current official Claude Code authentication options and terms
  for external integrations.
- [ ] Distinguish Claude API access, Claude Code account access, and any local
  CLI or service process; do not assume they are interchangeable.
- [ ] Define login, logout, re-authentication, status, entitlement/error, and
  unavailable-service states.
- [ ] Define the supported transport, streaming, tool-call, approval,
  cancellation, session, and process-lifecycle boundaries.
- [ ] Define secure handling for credentials, callbacks, local state, logs,
  exports, sync, and user-visible diagnostics.
- [ ] Compare the Claude Code approach with the shared T69 adapter contract and
  record platform limits, especially desktop/mobile differences.
- [ ] Provide a proof-of-concept and real-provider acceptance plan before any
  production implementation.

## Implementation Details

This subtask begins as an evidence-gathering and boundary-definition task.
It must not infer that Claude Code exposes the same subscription-backed
integration surface as Codex. The final recommendation should state whether
Obsidian AI should launch an authenticated local CLI/process, use an official
API, use a supported OAuth flow, or defer the service.

Any implementation must reuse T69's common provider status and credential
privacy rules while preserving Claude-specific capabilities and limitations.
