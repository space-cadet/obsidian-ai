## Description

Validates the accuracy of our `estimateTokens()` function against
provider-reported token usage. The Aug 27 run showed ~64% over-estimation on
average — this experiment determines whether that bias is consistent across
configurations or varies by strategy.

## Method

1. Select 5 representative configurations from the Pareto frontier (T64a):
   - Baseline (no optimization)
   - Aggressive elide (max savings)
   - Balanced elide + budget
   - Preserve mode
   - Compaction (if implemented)
2. For each config × fixture combination:
   a. Run Level 1: record `estimated_tokens`
   b. Run Level 2 (`--live --provider openrouter`): record `actual_prompt_tokens`
   c. Compute delta: `(actual - estimated) / estimated × 100`
3. Report: per-config accuracy, per-fixture accuracy, overall bias

## Key Questions

1. Is the 64% over-estimation consistent across all configs, or does it vary?
2. Does elide mode make estimates *more* or *less* accurate?
3. What's the cost to validate (OpenRouter GPT-4o-mini at ~$0.01/fixture)?
4. Should we tune `estimateTokens()` based on these findings?

## Results — 2026-08-29

The live harness was run against OpenRouter using `openai/gpt-4o-mini`. It
completed 16 requests: four strategies across four fixtures. The runner
reported the following prompt-token counts:

| Fixture | Strategy | Estimated | Actual | Difference |
|---|---:|---:|---:|---:|
| attachment-session-15-turns | baseline | 19,597 | 220 | -98.88% |
| attachment-session-15-turns | elide | 19,597 | 780 | -96.02% |
| attachment-session-15-turns | preserve | 19,597 | 14,668 | -25.15% |
| attachment-session-15-turns | budget | 4,793 | 55 | -98.85% |
| coding-session-30-turns | baseline | 2,817 | 799 | -71.64% |
| coding-session-30-turns | elide | 2,817 | 1,379 | -51.05% |
| coding-session-30-turns | preserve | 2,817 | 1,924 | -31.70% |
| coding-session-30-turns | budget | 2,817 | 799 | -71.64% |
| grammar-migration-13-turns | baseline | 28,720 | 3,111 | -89.17% |
| grammar-migration-13-turns | elide | 28,720 | 1,863 | -93.51% |
| grammar-migration-13-turns | preserve | 28,720 | 30,544 | +6.35% |
| grammar-migration-13-turns | budget | 5,871 | 109 | -98.14% |
| research-session-20-turns | baseline | 2,200 | 610 | -72.27% |
| research-session-20-turns | elide | 2,200 | 980 | -55.45% |
| research-session-20-turns | preserve | 2,200 | 1,668 | -24.18% |
| research-session-20-turns | budget | 2,200 | 610 | -72.27% |

The average difference was -65.2%. The estimate was higher than the provider
count in 15 of 16 requests. The one under-estimate was the grammar fixture in
preserve mode (+6.35%). The runner reported an estimated cost of about
`$0.01–$0.05` per fixture, but no provider billing amount was available in the
local output, so the cost acceptance item remains open.

### Recommendation

Do not apply one global correction factor to `estimateTokens()` yet. The gap
varies by fixture and strategy, and one preserve-mode case was slightly
under-estimated. When provider usage is available, T48d should show that value
as the source of truth. Otherwise, it should show the local value clearly as
an estimate.

### Expanded validation — 2026-08-29

The missing fifth configuration was added as `compaction`: a deterministic
local compaction projection with a derived summary block and the newest four
messages preserved. This measures the provider payload produced by the
projection; it does not include a separate LLM summarization request, so the
production compaction-operation cost remains a separate concern.

| Fixture | Strategy | Estimated | Actual | Difference | Provider cost |
|---|---:|---:|---:|---:|---:|
| attachment-session-15-turns | compaction | 5,677 | 4,252 | -25.10% | $0.00032700 |
| coding-session-30-turns | compaction | 771 | 592 | -23.22% | $0.00009480 |
| grammar-migration-13-turns | compaction | 7,762 | 9,201 | +18.54% | $0.00070455 |
| research-session-20-turns | compaction | 1,080 | 852 | -21.11% | $0.00013380 |

The expanded run completed 20 requests across five strategies and four
fixtures. Provider-reported cost from OpenRouter `usage.cost` was
`$0.00628440` for the benchmark. A separate one-request metadata probe cost
`$0.00000240`, for `$0.00628680` in the complete validation activity.

Across all 20 requests, the average estimate difference was `-54.7%`, ranging
from `-98.88%` to `+18.54%`. The provider count exceeded the local estimate in
two cases: grammar migration with preserve (`+6.35%`) and the deterministic
compaction projection (`+18.54%`). This further supports provider usage as the
display source of truth and rejects a single estimator correction factor.

The live run used `openai/gpt-4o-mini` through OpenRouter. The API key was
provided through the process environment only and was not written to the
repository or Memory Bank.
