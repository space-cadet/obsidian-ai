## Description

Enable the LLM to directly edit, create, and append to Obsidian notes via native tool calling using the Vercel AI SDK. Instead of returning edited content as text for the user to manually apply, the agent invokes structured tools that modify the vault directly — similar to how agentic code IDEs (Cursor, Claude Code) operate.

The user retains control via an `autoApply` setting (off by default): when off, each tool call is surfaced as a pending action in the chat UI that the user must approve before execution.

## Completion Criteria

### Tool Definitions
- ⬜ `read_note` tool — reads note content for the agent's context
- ⬜ `edit_note` tool — replaces full note content (calls `vault.modify`)
- ⬜ `append_to_note` tool — appends content to end of note (calls `vault.modify`)
- ⬜ `create_note` tool — creates new file (calls `vault.create`)
- ⬜ Zod schemas for all tool parameters (`path`, `content`, `noteName`)
- ⬜ Tool descriptions tuned so the LLM knows when to use each tool
- ⬜ **Tools defined as pure Zod schemas WITHOUT `execute` functions** — execution happens in `ToolExecutor` after user approval

### Agent Core
- ⬜ `AgentLoop` class — orchestrates multi-step `streamText` calls with our own loop logic
- ⬜ `ToolExecutor` — executes tool handlers against vault with error handling and path validation
- ⬜ SDK-agnostic `StreamEvent` union — insulates UI from SDK event type changes
- ⬜ `maxAgentSteps` counter prevents infinite loops (default 5)

### API Layer
- ⬜ `ChatApiManager.streamChatWithTools()` — single-step `streamText({ tools })` yielding `StreamEvent`
- ⬜ Keep existing `streamChat()` as text-only fallback for unsupported providers
- ⬜ Handle `text-delta`, `tool-call`, `tool-result`, `tool-error` events from `fullStream`
- ⬜ Provider compatibility check — disable tools for providers/models that don't support function calling

### Chat Loop & UI
- ⬜ `ChatApp` creates `AgentLoop` instance per conversation
- ⬜ Streaming state machine handles text + tool events in sequence
- ⬜ Pending tool calls render as action cards in the chat stream ("Edit Vocabulary Log? [Approve] [Reject]")
- ⬜ On approve: `ToolExecutor` runs, result fed back to `AgentLoop`, stream continues
- ⬜ On reject: skip execution, feed rejection message back to model, stream continues
- ⬜ Tool results are appended to conversation history for model continuation

### Settings
- ✅ `enableAgentTools: boolean` setting (default `true`) — master toggle
- ✅ `autoApply: boolean` setting (default `false`) — when true, tools execute without confirmation
- ✅ `maxAgentSteps: number` setting (default `5`) — limits tool call roundtrips per message

### System Prompt
- ⬜ Dynamic system prompt includes tool availability description
- ⬜ Prompt instructs model to return ONLY revised content when using `edit_note`
- ⬜ Prompt clarifies that `read_note` is available for multi-step reasoning

### Safety
- ⬜ Tool execution errors surface as user-visible notices, not silent failures
- ⬜ `maxAgentSteps` hard cap prevents infinite tool loops
- ⬜ Tool handlers validate paths (no directory traversal outside vault)
- ⬜ Create-note tool checks for existence; overwrite confirmation when autoApply is off

## Architecture

```
User: "Rewrite the intro of @Vocabulary Log"
        │
        ▼
ChatApp creates AgentLoop(messages, tools)
  │
  ├── buildSystemPrompt()  → includes tool descriptions
  ├── resolveContextItems() → context XML block
  └── AgentLoop.runStep()
        │
        ▼
  streamText({ model, messages, tools, stopWhen: stepCountIs(1) })
        │
        ▼
  text-delta → "I'll rewrite that for you..."
        │
        ▼
  tool-call → edit_note({ path: "Vocabulary Log.md", content: "..." })
        │
        ▼
  ChatApp renders PendingToolCard:
    "✏️ Edit Vocabulary Log   [Approve] [Reject]"
        │
        ├── User clicks [Approve]
        │   ToolExecutor.edit_note() → vault.modify()
        │   Result appended to messages
        │   AgentLoop.runStep() again
        │   LLM continues: "Done! I've tightened the intro..."
        │
        └── User clicks [Reject]
        │   Rejection appended to messages
        │   AgentLoop.runStep() again
        │   LLM continues: "Understood, I won't modify the note..."
```

## Design Decisions (Robustness-First)

1. **Manual loop around `streamText`** — `ToolLoopAgent` is experimental. We own the loop.
2. **Pure Zod schemas (no `execute`)** — LLM interface separate from vault operations.
3. **SDK-agnostic `StreamEvent` union** — If v7 changes event shapes, only `api.ts` changes.
4. **`AgentLoop` orchestrates, `ChatApp` renders** — Testable loop logic, replaceable UI.

## Context

The Vercel AI SDK v6.0.174 (currently installed) removed `maxSteps` from `streamText` and introduced `ToolLoopAgent` as an experimental abstraction. For robustness, we avoid `ToolLoopAgent` and instead call `streamText({ tools, stopWhen: stepCountIs(1) })` repeatedly, managing the loop ourselves. This insulates us from experimental API churn.

Key SDK references:
- `streamText` with `tools`: https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling
- `tool` helper: defines Zod schema (no execute for approval flow)
- `fullStream`: yields `TextStreamPart` union (text-delta, tool-call, tool-result, tool-error)

## Notes

- **arxivite does NOT have this feature** — its "tool registry" is imperative intent routing (app decides which function to run), not LLM-native tool calling.
- **Provider support**: OpenAI, Anthropic, Google Gemini, and DeepSeek all support tool calling. Ollama support varies by model (Llama 3.1+, Qwen 2.5+ work well).
- **Bundle impact**: Minimal — `zod` is already installed, no new runtime dependencies.
- **Alternative considered**: XML tag parsing (`<edit-note>...</edit-note>`) was rejected in favour of native tool calling for long-term robustness.
