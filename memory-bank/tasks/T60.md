## Description
Replace the duplicated, transport-specific tool wiring with one canonical
capability registry and a shared validated execution pipeline. Preserve the
separate ownership of approval/audit policy (T38), provider integrations
(T39), orchestration decomposition (T46), advanced vault tools (T17), and
compaction retrieval (T48c).

## Current State — 2026-08-25

Commit `68dc915` added a typed registry adapter, provider normalization,
availability filtering, OpenResponses projection support, and focused tests.
The registry is not yet the source of truth for execution: `ToolExecutor`
still owns dispatch, and the provider path still reduces definitions to raw
AI SDK tools. T60a is therefore incomplete; T60b's protocol fix is complete,
while T60c remains paused behind the execution gate.

### Cross-loop transport blocked by protocol bugs — 2026-08-25

Two concrete bugs in the OpenResponses loop prevent transport parity from
being testable:

1. **Duplicate input submission:** `streamAgentResponse({ input, tools })` is
   inside the `while` loop, causing full conversation resubmission on every
   tool round.
2. **Discarded continuation ID:** `previousResponseId` is accepted by
   `continueWithToolResult()` but never serialized to the request body.
   Continuations are sent as brand-new stateless requests.

These are protocol-level bugs, not registry bugs. T60b fixed them across
`OpenResponsesLoop.ts` and `AgentApiManager.ts`; transport/lifecycle
observability follow-up is tracked by T60e.

### Follow-up: provider-adaptive streaming — 2026-08-25

T60e records a separate-branch follow-up for the tool-event lifecycle exposed
by T60b: incremental native/OpenResponses tool events, provisional display,
complete-argument validation, and provider-aware progress states. T60e owns the
transport/lifecycle contract; T15 owns the associated chat UI presentation.

## Acceptance Criteria
- [ ] One canonical definition owns schema, description, risk, availability,
  handler, preview, formatting, audit redaction, and concurrency metadata.
- [ ] A test proves that a registry definition reaches execution and returns
  the same result as the existing `ToolExecutor` path.
- [ ] AI SDK, OpenResponses, prompt summaries, approval cards, and dispatch are
  derived from the resolved registry.
- [ ] Every transport validates and executes calls through one fail-closed
  pipeline with structured errors and cancellation.
- [ ] Direct chat, remote-agent, and council flows preserve all calls and
  matching results.
- [ ] Contract tests cover registry, transport, policy, execution, rendering,
  persistence, and unavailable-capability behavior.

## Implementation Details
The target pipeline is: resolve, validate, authorize, preflight, approve,
execute, validate result, audit, model-render, and persist the full result.
Reads may use bounded concurrency; mutations are serialized by target and use
optimistic concurrency where existing content can change.
