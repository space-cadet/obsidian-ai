## Description

Enable the Obsidian AI plugin to connect to remote OpenClaw agents (and potentially other OpenResponses-compatible agent endpoints) as a chat client. The plugin becomes a bidirectional client: it sends user messages to the agent, receives streaming responses, and executes tool calls requested by the agent against the local Obsidian vault.

This transforms the chat panel from a local LLM interface into a persistent agent channel where agents like Ember (Kimi Claw) can read, edit, create, and append to notes via the existing T13 tool infrastructure.

## Architecture

```
User types in Obsidian chat
        │
        ▼
ChatApp.handleSend()
  │
  ├── resolveContextItems() → context XML block
  ├── buildSystemPrompt() → agent instructions
  └── AgentApiManager.streamAgentResponse()
        │
        ▼
  POST /v1/responses (SSE)
  {
    model: "openclaw:main",
    input: [...messages],
    tools: [read_note, edit_note, append_to_note, create_note],
    stream: true,
    user: <session-key>
  }
        │
        ▼
  SSE events:
  ├── response.output_text.delta → "I'll check that note..."
  ├── response.output_item.added
  │     { type: "function_call", call_id: "...", name: "read_note", arguments: "{...}" }
  └── response.completed
        │
        ▼
  Tool detected? → ToolExecutor.execute()
        │
        ▼
  POST /v1/responses (follow-up)
  {
    input: [
      { type: "function_call_output", call_id: "...", output: "<note content>" }
    ],
    previous_response_id: <last-response-id>
  }
        │
        ▼
  Agent continues with tool result...
```

## Design Decisions

1. **OpenResponses over OpenAI Chat Completions** — OpenResponses supports client-side tools natively. OpenAI endpoint is stateless and one-directional.
2. **Reuse T13 infrastructure** — ToolExecutor, tool definitions, and pending-approval UI are already built. We serialize to OpenResponses format instead of Vercel AI SDK format.
3. **AgentApiManager mirrors ChatApiManager** — Same pattern: constructor takes settings+app, methods for streaming, connection test, settings update.
4. **Session key as `user` field** — OpenResponses derives stable session key from `user`. We generate one on first connect and persist it.
5. **Manual tool loop** — Same robustness-first approach as T13. We own the loop, not the SDK.

## Notes

- **Security**: The agent endpoint is full operator access. Keep it on private network/Tailscale.
- **Fallback**: If agent is unreachable, show error and offer to switch provider.
- **Bundle impact**: No new dependencies — we use native `fetch` + SSE parsing.
- **Future**: Could support multiple agent endpoints (work, personal, research agents).
- **Agent names**: The user has two agents — Ember (Kimi Claw, phone/VPS) and Cloudy (云忆, cloud instance). Both could be targets.
