## Current Tool-Transport Boundary — 2026-08-25

- **BUG: `previous_response_id` is discarded.** `OpenResponsesLoop` captures
  `lastResponseId` from `finish` events and passes it to
  `AgentApiManager.continueWithToolResult()`, but the manager never serializes
  it. `AgentApiOptions` has no `previousResponseId` field, and
  `streamAgentResponse()` never adds it to the request body. The installed
  OpenClaw gateway supports this field; the plugin simply never sends it.
  This forces every continuation to be sent as a brand-new stateless request,
  which causes the full original input to be replayed on every tool round.
- **BUG: Duplicate input submission.** `streamAgentResponse({ input, tools })`
  is called inside the `while` loop at `OpenResponsesLoop.ts:92-108`. After
  each tool execution, the loop returns to the top and resubmits the complete
  original conversation history. A 17-step tool chain resends the original
  input 17 times — the direct cause of the 500k-token blowup observed on
  2026-08-25.
- The OpenResponses serializer needs a compatibility test against the current
  canonical tool definition shape.
- Remote agents must receive the resolved provider-aware registry, not only
  the built-in `noteTools` object.
- Multiple function calls, malformed arguments, rejection, cancellation, and
  continuation results require parity tests with native AI SDK chat.
- T60b implements transport parity while this task remains the product-level
  owner of remote-agent connectivity.

## Streaming Observability Follow-up — T60e

The current OpenResponses parser and loop collect function calls until the
response stream completes before notifying the UI. Argument-delta events are
not yet surfaced. T60e owns the separate-branch follow-up for provisional tool
display, complete-argument execution gating, and generic provider-waiting
progress; T14 remains the owner of remote connectivity and SSE correctness.
