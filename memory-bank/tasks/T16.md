## Description

Enable a **group chat mode** where multiple agents participate in a single shared conversation. The user types once, and one or more agents respond — either sequentially, in parallel, or based on mentions (`@Cloudy fetch arxiv`).

This transforms the chat from isolated 1:1 channels into a collaborative "council" where agents can reference each other's responses, build on shared context, and handle different aspects of a query.

## Architecture

### Group Chat Data Flow (Unified ChatApp)
```
User types in ChatApp (1:1 or council mode):
"What are recent LQG papers? @Cloudy fetch the PDF too."
        │
        ▼
[1:1 Mode] → send to active profile's ChatEngine → normal flow
        │
[Council Mode] → parseAndRoute(text)
        │
        ├── "What are recent LQG papers?" → route to ALL agents
        └── "@Cloudy fetch the PDF too." → route to Cloudy only
                │
                ▼
        Orchestrator.dispatch(message, thread)
        ├── Sequential mode (default):
        │   ├── Send to Gemini → wait → append to thread
        │   ├── Send to Cloudy → wait → append to thread
        │   └── Send to Ember → wait → append to thread
        │
        └── Parallel mode (future):
            ├── Send to Gemini ──┐
            ├── Send to Cloudy ──┼── Promise.all → append all
            └── Send to Ember ───┘
                │
                ▼
        Context Builder (per agent)
        ├── Full Transparency:
        │   └── Agent sees: [User msg, Gemini response, Cloudy response, ...]
        │
        └── Isolated:
            └── Agent sees: [User msg, Agent's own previous responses only]
                │
                ▼
        Each agent processes with their profile via streamChat()
                │
                ▼
        Responses rendered in unified thread with identity badges
```

### Orchestrator Class (Implemented)
```typescript
class Orchestrator {
  engines: AgentEngine[];
  mode: 'sequential' | 'parallel';
  contextStrategy: 'full' | 'isolated';

  parseAndRoute(text: string): { targets: AgentEngine[], cleanText: string }
  buildContext(agentId: string, thread: ChatMessage[], cleanText: string): Message[]
  dispatch(text: string, thread: ChatMessage[]): AsyncGenerator<AgentResponse>
  
  // Sequential: yields responses one at a time
  // Parallel: launches all, yields as they complete
}
```

## Design Decisions

1. **Unified UI over separate panels** — User explicitly requested same ChatApp for all chat types. Council toggle switches mode in-place.
2. **All-or-nothing toggle as MVP** — Clicking "Council" adds ALL profiles. Individual add/remove is Phase 10.
3. **Sequential as default** — Agents can build on each other's responses. Parallel mode exists in code but not wired.
4. **Full transparency as default context** — Agents see complete conversation. Isolated mode configurable.
5. **Tool calling in council mode** — Now enabled via AgentLoop (same class as single-user path). Auto-approve only; manual approval UI deferred.
6. **Stale orchestrator fix** — handleSend dependency array MUST include orchestrator, participants. React useMemo alone insufficient due to closure capture.

## Implementation Notes

- **UI complexity**: Unified ChatApp is harder than separate panels but matches user vision.
- **React dependency arrays**: Critical for group chat. handleSend deps must include orchestrator, participants.
- **SSE concurrency**: Not yet an issue (sequential mode). Parallel mode will need testing.
- **Context window limits**: With full transparency, each agent sees growing conversation. May need truncation.
- **Error isolation**: If one agent fails, others continue. Error shown with agent name attribution.
- **Participant removal mid-conversation**: UI shows × button but doesn't reconfigure. Needs handleRemoveParticipant to abort pending responses.
