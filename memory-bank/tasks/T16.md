## Description

Enable a **group chat mode** where multiple agents (Gemini, Cloudy, Ember) participate in a single shared conversation. The user types once, and one or more agents respond — either sequentially, in parallel, or based on mentions (`@Cloudy fetch arxiv`).

This transforms the chat from isolated 1:1 channels into a collaborative "council" where agents can reference each other's responses, build on shared context, and handle different aspects of a query.

Requires T15 (Tabbed Chat) as foundation — group chat reuses the multi-profile infrastructure but adds orchestration and identity-aware messaging.

### Phase 6: Parallel vs Sequential Response Modes
- ⬜ **Sequential mode** (default): Agents respond one after another
  - User sends message → Agent A responds → Agent B sees A's response → Agent B responds → ...
  - Pros: Agents can reference each other's work
  - Cons: Slower (linear latency)
- ⬜ **Parallel mode**: All agents respond simultaneously
  - User sends message → All agents receive same prompt → All respond concurrently
  - Pros: Fastest response time
  - Cons: Agents can't reference each other
- ⬜ **Hybrid mode**: Parallel for independent queries, sequential for follow-ups
- ⬜ Mode toggle in chat UI (per-conversation setting)

## Architecture

### Group Chat Data Flow
```
User types in group chat:
"What are recent LQG papers? @Cloudy fetch the PDF too."
        │
        ▼
Mention Parser
├── "What are recent LQG papers?" → route to ALL agents
└── "@Cloudy fetch the PDF too." → route to Cloudy only
        │
        ▼
Orchestrator.dispatch(message, agents)
├── Sequential mode:
│   ├── Send to Gemini → wait for response → append to thread
│   ├── Send to Cloudy → wait for response → append to thread
│   └── Send to Ember → wait for response → append to thread
│
└── Parallel mode:
    ├── Send to Gemini ──┐
    ├── Send to Cloudy ──┼── Promise.all → append all responses
    └── Send to Ember ───┘
        │
        ▼
Context Builder (per agent, per strategy)
├── Full Transparency:
│   └── Agent sees: [User msg, Gemini response, Cloudy response, ...]
│
└── Isolated:
    └── Agent sees: [User msg, Agent's own previous responses only]
        │
        ▼
Each agent processes with their ChatEngine
        │
        ▼
Responses rendered in unified thread with identity badges
```

### Orchestrator Class
```typescript
class Orchestrator {
  engines: Map<string, ChatEngine>;  // agentId -> ChatEngine
  mode: 'sequential' | 'parallel';
  contextStrategy: 'full' | 'isolated';

  async handleUserMessage(message: string, mentions?: string[]): Promise<void> {
    const targets = mentions?.length > 0
      ? mentions.map(id => this.engines.get(id))
      : Array.from(this.engines.values());

    if (this.mode === 'parallel') {
      const responses = await Promise.all(
        targets.map(engine => this.sendToAgent(engine, message))
      );
      this.appendResponses(responses);
    } else {
      for (const engine of targets) {
        const response = await this.sendToAgent(engine, message);
        this.appendResponse(response);
      }
    }
  }

  private buildContext(agentId: string): Message[] {
    if (this.contextStrategy === 'isolated') {
      return this.thread.filter(m =>
        m.role === 'user' || m.agentId === agentId
      );
    }
    return this.thread; // full transparency
  }
}
```

## Design Decisions

1. **Mention-based routing as MVP** — Simplest to implement, most predictable UX. User explicitly tags who should respond.
2. **Sequential as default mode** — Agents can build on each other's responses. Parallel mode is an opt-in optimization.
3. **Full transparency as default context** — Agents can reference each other's work. Isolated mode is for privacy-sensitive scenarios.
4. **Orchestrator owns the loop, not individual engines** — Each `ChatEngine` is still a single-provider instance. The `Orchestrator` coordinates multiple engines.
5. **Tool locking per file, not globally** — Two agents can edit different files simultaneously. Only same-file edits conflict.
6. **Lazy engine initialization** — Engines are only created when an agent is first mentioned or when group chat starts.

## Implementation Notes

- **UI complexity**: Group chat is the hardest UI problem. Start with a dedicated "Group Chat" panel mode, don't try to merge it into single-chat tabs immediately.
- **SSE concurrency**: Multiple agents streaming simultaneously means multiple SSE connections. Browsers typically allow 6-10 concurrent connections per domain. Remote agents on different hosts (Tailscale IPs) avoid this limit.
- **Message ordering**: In parallel mode, responses may arrive in any order. UI should show them as they arrive, not wait for all.
- **Context window limits**: With full transparency, each agent sees a growing conversation. May hit token limits faster. Consider summarization or truncation.
- **Error isolation**: If one agent fails (e.g., Cloudy offline), others should continue responding. Show offline status for the failed agent.
