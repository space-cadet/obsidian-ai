## Description

Implement Obsidian AI's host side of the Integration Provider API: a stable
registry for installed peer plugins, capability discovery, tool availability,
host-enforced approval/audit policy, and typed result/progress handling.

## Acceptance Criteria

- [x] Define runtime-validated provider/capability contracts with explicit API
  version and risk classification.
- [x] Discover compatible providers at plugin load and layout readiness.
- [x] Register enabled namespaced read-only tools and report incompatibility.
- [x] Route read-only provider calls through ToolExecutor and the tab-scoped
  approval/result loop.
- [x] Provide opt-in Integrations settings without credential display.
- [ ] Render provider calls through generic pending-operation and inline
  progress/result cards, including redacted typed previews and clear provider
  unavailability feedback.
- [ ] Show the active tool-policy state compactly in the chat UI once T38
  replaces the current binary auto-apply setting.
- [ ] Cover version negotiation, duplicate names, provider loss, policy
  classification, and rejected/failed execution with focused tests.

## Implementation Details

- Prefer a documented peer-plugin API and a host adapter/registry over dynamic
  loading of third-party bundles within Obsidian AI.
- Keep provider descriptors JSON-serializable at the model boundary. Runtime
  execute/progress callbacks stay inside the trusted Obsidian plugin process.
- The host owns final risk classification. Provider declarations inform UI and
  compatibility but cannot bypass confirmation for a remote or destructive
  operation.
- The first UI slice comprises an Integrations settings list and generic cards;
  it must not duplicate a provider's normal configuration or manual UI.
