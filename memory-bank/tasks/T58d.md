## Description

Resolve the post-delivery sync-panel issues found during tablet review and
source audit. Unify planning, dry-run, real-sync, plugin-data, and index-rebuild
progress so the user can see what is being scanned, planned, transferred, or
reconciled.

The approved implementation slice is complete and the remaining acceptance
work is explicitly recorded below. A follow-up audit also confirmed that the
Rebuild action currently rebuilds only the chat-session index.

## Acceptance Criteria

- [x] Planning stages show visible progress before item transfers begin.
- [x] Dry-run planning includes selected plugin-data components without writing
      local, remote, or index state.
- [x] Plugin-data state remains distinct from the chat-session SyncIndex and
      is shown separately in the plan and result.
- [x] One stable UI row represents each operation and transitions through
      pending, active, done, skipped, or error without duplicates.
- [x] The shimmer is shown only on the latest active operation.
- [x] The progress bar remains visible at 100% after completion and shows a
      final summary until the next run or dismissal.
- [x] Index rebuild shows planning progress, total work, completed work,
      cancellation, and a final result.
- [x] Rebuild avoids repeated local/remote scans and uses bounded concurrency
      for independent transfers.
- [ ] Conflicts produce partial/attention-required status rather than
      reporting complete.
- [ ] Focused tests cover dry-run plugin-data planning, progress transitions,
      rebuild progress, duplicate prevention, and conflict status.

## Implementation Details

Use a shared progress event contract with explicit phases and stable operation
identifiers. The initial planning event may be indeterminate until the plan
total is known; subsequent events report completed and total.

The chat-session index remains session-only. Plugin files use their separate
identity-scoped shared state. A dry run reads and compares both state models
but does not mutate either one.

Rebuild should reuse the computed plan, replace repeated membership scans with
maps or sets, and apply the existing bounded concurrency helper where safe.
The UI should retain the final 100% state after the operation settles.

The current Rebuild action still applies only to chat-session entries and
writes the session-only SyncIndex. Plugin data is synced and planned through
its separate identity-scoped shared state, but it has no equivalent rebuild
phase yet. A future plugin-data rebuild must scan and reconcile that state
separately, preserve credential/local-only boundaries, and report its results
without adding plugin files to the chat-session index.
