## Problem Statement
`src/components/ChatApp.tsx` has grown to **1,948 lines / 63 KB**. It contains:
- 24+ `useState` declarations
- 10 `useRef`s
- 8+ `useEffect` hooks
- ~25 handler functions
- ~300 lines of JSX

This violates single-responsibility principle and makes the component unmaintainable.

## Root Cause
Every chat feature (sessions, streaming, context, group chat, tool approval, editing, export, zen mode, debate mode, auto-save, title generation) is crammed into one component. State, logic, and UI are not separated.

## Decisions

### Single Hook vs. Multiple Hooks
Extracted ALL message action handlers into a single `useMessageActions` hook rather than splitting into `useSendActions`, `useNoteActions`, `useToolActions`, etc. Rationale:
- These handlers share the same dependency surface (plugin, orchestrator, session refs, controller ref, etc.)
- Splitting would create 4–5 hooks each needing the same 20+ parameters
- One hook keeps the call site in ChatApp clean: `const actions = useMessageActions(deps)`
- Future: if the hook grows beyond 1,500 lines, reconsider splitting by domain.
  Its current size is 1,309 lines after T43 and remains below that explicit
  reconsideration threshold.

### Test Strategy
- Wrote tests for simpler handlers first (note actions, editing, stop, tool approval)
- Basic test for group chat path of `handleSend`
- Deferred comprehensive `handleSend` testing (AgentLoop, OpenResponsesLoop, standard streaming) — mock setup would be 200+ lines for marginal value
- `handleRetry` tests mock `handleSend` rather than testing the full resend flow

## Open Questions
1. Should `useMessageActions` be split into `useSendActions` + `useNoteActions` + `useToolActions`? (see Decisions above — defer until hook >1,500 lines)
2. Should `handleSend` accept a `getHistory()` callback instead of reading `messagesRef` directly? Would make testing easier but adds indirection.
3. Should Obsidian-specific rendering and host actions move behind the T44 host boundary before Phase 5 stories are created? Yes for standalone preview work; keep the production adapter behavior unchanged.
