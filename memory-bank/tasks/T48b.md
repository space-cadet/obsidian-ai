# Task: T48b — Tool-Result Replay Limits and Canonical Serialization
*Created: 2026-08-23 02:02:32 IST*
*Status: 🔄 ACTIVE*
*Last Updated: 2026-08-23 17:05:26 IST*

## Objective
Keep full tool results for UI/export while sending bounded, canonical tool
representations to the model. Prevent duplicate `toolCalls`/`contentParts`
serialization in request history.

## Acceptance Criteria
- [x] Every tool result has a token-based replay limit
- [x] Oversized results are truncated with an explicit marker
- [x] Model history uses one canonical tool-call/result representation
- [ ] Tool-call/result pairing remains valid after truncation or compaction
- [x] Large memory listings are bounded by the replay limit

## Implementation Slice — 2026-08-23

Tool results are now truncated only in model replay, retaining the head and
tail plus an explicit marker. Full results remain in the persisted message for
UI display/export. The remaining pairing invariant and semantic summarization
work is tracked separately from this safe size cap.

The implementation was merged to `main` in `6a205b9` (PR #5), and the live
compaction test confirmed that the user-visible transcript remained available
for export. Pairing across a compacted model-history projection still needs
focused acceptance coverage.

## Audit update — 2026-08-25

Pairing acceptance must include multiple calls emitted in one native step and
equivalent canonical serialization through AI SDK and OpenResponses transports.

**Result size lesson:** The 500k-token incident involved `search_notes` returning
100 matches with full metadata per call (~3k tokens each). Even with bounded
replay, large result arrays are expensive. Consider lowering `search_notes`
default limit (100 → 20) and teaching the model to batch lookups via
`search_note_content` (one call with multiple terms).
