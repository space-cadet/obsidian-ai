# Task: T24b — Idempotent Transcript Writes and Index Reconciliation

*Created: 2026-10-19 15:12:00 IST*
*Last Updated: 2026-10-19 21:02:15 IST*

**Status:** 🔄 **IN_PROGRESS**
**Priority:** HIGH
**Parent:** T24

## Problem

The 2026-10-19 09:28 UTC on-device health report found repeated message IDs in
nine transcripts, two index/transcript count mismatches, and 57 unindexed
transcripts. Fifteen unindexed transcripts were empty. Existing code already
serializes lifecycle saves, checks the on-disk prefix before appending, and
removes exact duplicate records before a full write. The report shows those
guards do not prevent every duplicate or index inconsistency.

The report is structural and contains no transcript text. It does not identify
the original cause or show whether repeated IDs have conflicting contents.

## Scope

Prevent these findings from being newly created by normal local persistence.
Existing user transcripts are out of scope: do not rewrite, restore, index, or
delete them as part of this task.

## Acceptance Criteria

- [x] Normal JSONL saves and explicit deletions use one staged transaction;
  low-level helpers cannot append or delete transcripts outside it.
- [x] Exact repeated records are handled idempotently. Conflicting records with
  one message ID are detected and surfaced without silently discarding either
  version.
- [x] Transcript and `sessions/index.json` updates use a crash-safe protocol
  supported by the Obsidian vault adapter, with startup completion or
  reconciliation after an interrupted save.
- [x] Empty transcript files are not created for zero-message sessions by
  normal saves, session allocation, or migration; the health check accepts an
  absent transcript only when the index count is zero.
- [x] Legacy migration removes exact duplicate IDs and rejects conflicting IDs
  before it starts writing converted files.
- [ ] Targeted coverage exercises retries, same-ID conflicts, concurrent saves,
  interruption between transcript and index writes, and empty-session creation.
- [x] Build and Android acceptance are recorded separately; no claim of device
  acceptance follows from a successful build alone.
