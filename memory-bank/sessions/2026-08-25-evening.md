## New Finding: search_note_content Performance Issue (Runtime)

During testing with T60b fix applied, user ran the same prompt that caused the
original 500k-token incident (Chinese vocabulary check). The agent now correctly
uses `search_note_content` instead of 17 sequential `search_notes` calls, but:

**Problem:** `search_note_content` is **O(n) over all markdown files** with:
- No persistent index — reads and scans every file every time
- No early termination — continues scanning after finding enough matches
- Sequential I/O — single-threaded file reads
- No timeout — can block for 10+ seconds on 800+ file vaults

**Behavior observed:** Agent calls `search_note_content` repeatedly with no
visible result (because each call takes too long), likely causing overlapping
scans and compounding the slowness.

**Root cause in code:**
```typescript
// ToolExecutor.ts:searchNoteContent()
for (const file of files) {
    content = await this.app.vault.read(file);  // Read entire file
    // Full scan + excerpt building
}
// No break when limit matches found
```

**This is a separate issue from T60b** — the protocol fix works, but the tool
itself is too slow for large vaults.

**Relation to T60d:** This validates the need for T60d (Token-Efficient Search
Defaults) and adds a performance dimension — not just token efficiency but
latency/timeout issues.
